# 真实账本 Dogfood 记录（v0.2 决策输入）

本文件规定 v0.1 之后、v0.2 范围冻结之前的真实账本使用协议。目的不是再验证一遍单元测试，而是回答一个问题：

> 在真实账户上，内核闭环是否比手工记账更快、更少错、更可审计？

结论必须来自实际使用数据，而不是功能愿望清单。没有这组数据，不排 v0.2 功能优先级。

## 安全边界

- 只用一份**账本副本**；原账本目录保持只读，不在 dogfood 中修改。
- 开始前做一次完整备份，并记录副本的 `ledger_revision`（`ledger-kernel status`）。
- 发现缺陷时记录 issue 并按正常流程修复；不要在 dogfood 过程中顺手改内核行为。
- 不把真实账本、`.ledger-kernel/`、证据文件或个人信息提交进仓库。

## 样本与时长

- 2–4 周，至少 20 笔真实交易。
- 覆盖四类：日常支出、收入、账户间转账、对错误交易的冲销/修正。
- 每笔都走完整闭环：提交草稿 → `validate` → `approve` → `commit`；不跳过 dry-run，不使用批量捷径。

## 每笔记录

| 日期 | draft_id | 提交→批准耗时 | dry-run 结果 | 阻断/警告 code | 是否手工改文件 | 观测/恢复 | 备注 |
| --- | --- | --- | --- | --- | --- | --- | --- |
|  |  | 秒 | pass / blocked |  | 是 / 否 |  |  |

“手工改文件”指绕过内核直接编辑账本后才完成记账；这是 v0.2 最需要知道的摩擦点。

## 每周汇总

在账本副本目录运行（全局参数放在子命令前）：

```bash
ledger-kernel --json status
ledger-kernel drafts list
ledger-kernel audit --limit 100
ledger-kernel observations list
ledger-kernel recovery status
```

记录：草稿状态分布、审计事件数、观测事件数、recovery 状态、平均确认耗时。

## 数据到 v0.2 的判据

按以下顺序判断，命中即调整优先级：

1. **出现 recovery、审计链异常或提交重复**：暂停新功能，先修复并补 ADR 与回归测试。
2. **提交→批准耗时中位数 > 60 秒，或同类字段反复填写**：优先做最小审核前端与草稿模板，而不是归因。
3. **dry-run 阻断 ≥ 30%，且集中在账户/契约**：优先做契约编辑与账户提示。
4. **观测事件 ≥ 3 次且原因不明**：才考虑接入 Git/OS audit 归因；否则降级。
5. **手工改文件 ≥ 20%**：先补前置校验、证据采集或草稿生成，不引入自动审核分级。

## 结论落在哪里

- 汇总结果写成 v0.2 范围文档或 ADR，放进本仓库 `docs/design/`；库外笔记只放过程记录，不作为规范。
- 结论至少包含：样本量、上述五项指标的实际值、据此否决了哪些候选功能。
