# 本地账户内核 v0.1：工程决策冻结与原型实施计划

- **文档状态**：工程决策草案，可作为 v0.1 原型实施基线
- **版本**：v0.1-implementation-plan
- **依据**：更新后的《[顶层设计摘要](./design-summary.md)》、本轮技术核对，以及《[本地账户内核_v0.1_设计规格草案](./v0.1-spec.md)》（修订版；仅供规格展开参考，其 v0.1-draft 前身基于已失效的旧摘要，已按本文校正）
- **用途**：把顶层原则收敛成可执行的工程决策、风险边界和纵向原型验收标准

> 本文区分三种状态：**[已接受]** 用户已明确接受或顶层设计已明确；**[建议冻结]** 为了让 v0.1 可实施而建议采用；**[待验证/待决]** 必须通过原型或后续产品决策解决。

---

## 0. 结论

下一步不再扩写宏观架构，而是做一个最小纵向原型：

**加载真实 Beancount 账本 → 建立 revision → 观察外部修改 → 接收交易草稿 → 完整 Dry-run → 人工确认 → 向唯一 `write_target` 追加 → 记录审计 → 重启恢复。**

v0.1 的首要目标不是证明"Agent 永远无法绕过内核"，而是证明：

1. 通过内核的自动化写入有严格的校验、确认、事务和审计。
2. 用户或 Agent 绕过内核修改账本后，内核能够发现内容变化、重新加载、失效旧草稿并提示。
3. 系统不会把 hash 误称为身份认证，也不会在无法确认来源时虚构操作者。
4. 内核不会静默覆盖外部修改；无法安全合并或恢复时进入人工处理状态。

### 1.1 `write_target` 的具体约束

[建议冻结]

- 使用相对账本根目录的规范化路径，例如 `transactions/kernel-import.beancount`。
- 初始化时确认该文件存在，且确实被账本根文件的 `include` 关系加载。
- 拒绝路径逃逸、指向账本目录外的符号链接和不明确的目标路径。
- 内核自动提交只在该文件末尾追加完整交易块，不改写其他 ledger 文件。
- 目标文件编码、换行风格和末尾换行策略在初始化时探测并保留。
- 若 `write_target` 不在当前加载闭包中，或账本配置发生变化使它脱离 include，停止写入并要求重新配置。

### 1.2 v0.1 明确不做的"自动审核分级"

更新后的顶层摘要已写明审核分级 MVP 阶段不做。因此，低风险自动提交/高风险人工确认只能作为后续版本设计方向，不属于 v0.1 验收项。

v0.1 固定流程：

`Submitted → Validated → NeedsHumanApproval → Approved → Committing → Committed`

不允许仅凭 `confidence`、商户白名单、金额阈值或账户契约自动批准。

## 2. 更新后的写入治理模型

### 2.1 三种写入路径

| 写入路径            | 例子                                    | 内核能控制什么                            | 内核必须做什么                                               |
| ------------------- | --------------------------------------- | ----------------------------------------- | ------------------------------------------------------------ |
| 受控自动化写入      | Agent 通过 MCP/API 提交草稿，由内核提交 | 校验、审批、revision、事务、审计          | 严格执行完整闭环                                             |
| 用户直接写入        | 用户用编辑器、Git 或脚本修改文件        | 无法阻止，也不应阻止                      | 发现变化、重新加载、失效旧草稿、记录观察事件                 |
| 用户授权 Agent 直写 | 用户让本地 Agent 直接编辑账本文件       | 通常无法保证操作系统层面区分 Agent 与用户 | 按外部变化处理；有可信来源事件时记录 Agent 声明，否则标记未知 |

内核是**自动化受控写入的唯一入口**，不是账本目录的绝对唯一写者。

### 2.2 发现、识别、归因是三件不同的事

必须分开定义：

- **发现（Detection）**：通过文件内容指纹发现 revision 漂移。
- **识别（Diff）**：在有前一版本内容或 Git 工作树基线时，计算具体文件差异。
- **归因（Attribution）**：基于 Agent 协作事件、系统进程审计、Git 提交信息等证据，判断可能来源。

SHA-256 只能用于内容完整性与版本识别，不能证明是谁写入。文件 watcher 也不保证能提供可靠的进程身份。

### 2.3 统一的来源归因枚举

建议在 `ExternalChangeObserved` 事件中使用：

| `source_kind`      | 含义                            | 说明                                                |
| ------------------ | ------------------------------- | --------------------------------------------------- |
| `kernel`           | 内核自身提交                    | 有 `commit_id`，可精确关联审计事件                  |
| `agent_reported`   | Agent 主动报告其执行了文件修改  | 记录 Agent 身份与声明；如无 OS 级佐证，不宣称强证明 |
| `git_commit`       | 与 Git commit 相关联            | 作为旁证，不等于操作者身份的强证明                  |
| `os_audit`         | 由操作系统审计记录识别进程/用户 | 依赖平台和明确启用的系统审计能力                    |
| `user_marked`      | 用户手动标记来源                | 表示用户声明，不应伪装成系统检测结果                |
| `external_unknown` | 外部变化，来源未知              | 必须是正常且可接受的最终状态                        |

另外增加 `attribution_confidence`：`verified / corroborated / claimed / unknown`。不要把它们压缩成一个含糊的 `source` 字符串。

### 2.4 顶层摘要中需要避免的过度承诺

当前摘要的"绕过内核的写入同样被观测、归因、可撤销"需要进一步收窄。原因：

1. 内核关闭期间的修改，只有在保存了上一个内容快照或 Git 历史时，才能可靠还原具体 diff。
2. Hash 漂移不能识别具体操作者。
3. 外部修改可能与后续编辑交错，内核无法保证逆补丁始终安全。
4. 用户直接编辑不能被内核擅自回滚。

建议替换为：

> 绕过内核的文件变化会在下次扫描时被发现；内核尽可能保存差异并依据可用证据标记来源，无法可靠归因时明确标记未知。内核写入可按提交记录撤销；外部修改只提供经冲突检查的恢复/反向补丁建议，由用户决定是否应用。

这一表达与"用户拥有最高编辑权"保持一致，也避免承诺技术上无法保证的能力。

## 3. 两套审计记录，不要混成一套

### 3.1 Kernel Commit Audit（内核提交审计）

记录内核明确执行的操作，字段至少包括：

- `event_id`、`commit_id`、`draft_id`、`validation_id`
- `actor`：批准该提交的用户主体
- `submitted_by`：提交提案的 Agent（如有）
- `occurred_at`
- `ledger_revision_before/after`
- `contract_revision`
- `write_target`
- `before_hash/after_hash`
- `patch_ref` 或提交交易内容摘要
- `approval_ref`

对于这类写入，来源和责任链应是确定的。

### 3.2 External Change Observation（外部变化观测）

外部直接编辑或同步引入的变化不能伪装成 `KernelCommit`。它应是单独事件，至少记录：

```json
{
  "event_type": "ExternalChangeObserved",
  "event_id": "evt_...",
  "detected_at": "2026-11-16T09:00:00+09:00",
  "previous_revision": "sha256:...",
  "current_revision": "sha256:...",
  "changed_files": ["transactions/kernel-import.beancount"],
  "diff_ref": "observations/obs_...diff",
  "source_kind": "external_unknown",
  "attribution_confidence": "unknown",
  "ledger_load_status": "valid",
  "action_required": false
}
```

如果只有 hash 变化，没有上一版本内容，则 `diff_ref` 可以为空，事件必须标明 `diff_unavailable`，不能伪造差异内容。

### 3.3 Git 的角色

Git 是很有价值的版本历史和证据来源，但不等于内核审计系统：

- 未提交的工作区变化不会自动形成 Git commit 历史。
- Git author 字段是提交元数据，不是可靠的操作系统身份认证。
- Git reset/rebase 可改写历史，不应作为内核提交责任链的唯一依据。

建议把"Git 历史即审计轨迹"改为"Git 历史是可选的版本历史补充；内核审计记录自己的提交，外部变化由观测日志记录"。

## 4. 外部变化后的内核状态机

每次内核启动、查询关键账户、校验草稿和提交前，都必须确保 revision 是最新的。文件 watcher 仅作为加速通知，不作为唯一检测机制。

```text
Clean
  └─ revision changed → ExternalChangeDetected
       ├─ full Beancount load valid → Reloaded / NewRevision
       │    ├─ invalidate stale drafts
       │    └─ record observation event
       └─ Beancount errors exist → LedgerInvalid
            ├─ block all controlled commits
            ├─ preserve current files and observation data
            └─ wait for user correction
```

处理原则：

- 外部变化合法且 Beancount 完整校验通过：接受新的 Ledger revision，重建派生状态，不覆盖文件。
- 外部变化造成语法或记账错误：如实报告，内核进入只读/阻断受控提交状态；用户仍可直接编辑修复。
- 旧草稿引用的 `ledger_revision` 或 `contract_revision` 发生变化：必须重新校验；旧批准默认失效，只有 ADR-013 的已知转移可沿用。
- 同步冲突或文件处于不完整中间态：不自动合并，不静默修复，进入人工处理。

## 5. 版本快照与外部 Diff：一个必须做的技术验证

若产品承诺观察外部变化，就必须有办法比较前后内容。仅保存当前 hash 不足以生成 Diff。

### 建议方案

- 对账本 root file 的完整 include 闭包建立 `ObservedRevision` 清单。
- 每个文件计算 SHA-256；清单按规范化相对路径排序后生成总 revision。
- 对 `write_target` 的内核提交，始终保存提交前快照和精确 patch。
- 对外部修改：若要支持 daemon 离线期间的 diff，必须在此前保留旧内容快照，或可依赖 Git 历史。v0.1 更可靠的做法是提供可选的内容寻址快照目录；这只是恢复/审计副本，不是当前财务真相源。
- 快照存储按文件内容 hash 去重，避免每次变化都复制整个账本目录。
- 设定保留策略和磁盘占用上限；超限时明确提示，不能静默删除尚未处理的审计基线。

### 待验证问题

Beancount `loader.load_file()` 返回 entries、errors、options map，但并不直接把"本次加载的所有物理输入文件列表"作为一个明确的第四返回值。因此，原型必须验证如何可靠枚举 include 闭包，不能凭猜测读取一个未承诺的 options 字段。

候选方案：

1. 基于 Beancount parser/loader 提供的 source metadata 或可用加载接口收集真实文件路径。
2. 独立解析 `include` 依赖图，但必须覆盖 Beancount 的 include 语义和路径规则，并用官方加载结果交叉验证。
3. 在版本固定后，对 loader 做一个极薄的受控适配/观测层。

该项列为原型中的 P0 技术验证。

## 6. Dry-run 与 Beancount Adapter 的实现约束

### 6.1 采用官方完整加载链路

当前官方 API 文档将 `beancount.loader.load_file()` 定义为打开输入文件、解析、运行 transformations 并校验，返回 `(entries, errors, options_map)`。内核应通过 Adapter 使用它，而不是自行判断 Beancount 完整语义。

建议 Adapter 边界：

```python
class BeancountAdapter(Protocol):
    def load(self, root_file: Path) -> LedgerLoadResult: ...
    def render_transaction(self, txn: ProposedTransaction) -> str: ...
    def extract_accounts(self, load: LedgerLoadResult) -> AccountCatalog: ...
    def extract_balances(self, load: LedgerLoadResult, as_of: date) -> list[AccountBalance]: ...
```

`LedgerLoadResult` 至少包含 entries、errors、options、source metadata、engine fingerprint 和输入文件清单（由适配层可靠收集）。领域层不直接暴露 Beancount 内部对象。

### 6.2 Dry-run 不要只用片段校验

推荐流程：

1. 固定当前 `ledger_revision` 与 `contract_revision`。
2. 为账本创建临时工作区，保留相对目录结构和 `include` 关系。
3. 仅向临时工作区内的固定 `write_target` 追加候选交易。
4. 对临时 root file 调用同一版本 Beancount 的完整加载与校验。
5. 根据 Beancount 输出错误和账户派生状态，再执行内核账户契约检查。
6. 生成受影响账户余额、交易块及文件变化的 Diff。
7. 丢弃临时工作区；真实账本不发生改变。

`load_string()` 适合字符串级测试，但不能直接替代含 include、文件路径和插件上下文的真实账本加载。必须用真实临时目录验证。

### 6.3 插件安全边界

Beancount 插件属于用户信任的代码执行环境。Agent 不得通过草稿指定插件、Python 模块、加载路径或运行代码。v0.1 只运行用户现有账本配置中的插件；原型需要验证临时工作区是否能正确复现插件依赖。若插件依赖绝对路径或外部副作用，必须在 UI/CLI 明确告知，不得假装 dry-run 与真实加载环境完全等价。

## 7. 提交原子性：保留为 P0 验证，不提前宣称绝对安全

单 `write_target` 使问题简单很多，但**不自动解决用户/Agent 同时编辑与内核提交之间的竞态**。普通编辑器不会遵守内核锁。

v0.1 可以保证：

- 内核实例之间串行提交。
- 每次提交前重新验证 ledger 与 contract revision。
- 提交前保留快照和 journal。
- 提交后再次检查目标文件与完整账本。
- 一旦发现外部漂移或结果不确定，进入 `RecoveryRequired`，不盲目重试。

v0.1 不能承诺：

- 对所有不配合内核锁的进程实现通用、跨平台的 compare-and-swap。
- 绝对阻止用户在提交瞬间编辑目标文件。
- 通过 watcher 可靠捕获每次短暂写入或准确识别写入进程。

### 原型需要比较两种提交原语

| 方式                      | 优点                                                     | 主要风险/验证项                                              |
| ------------------------- | -------------------------------------------------------- | ------------------------------------------------------------ |
| 同目录临时文件 + 原子替换 | 写入结果通常是整文件原子切换；易做写前快照               | 最后一次 hash 检查与 replace 之间仍有竞态；可能覆盖恰好并发发生的外部编辑 |
| `O_APPEND` 追加写         | 避免以内核生成的旧整文件覆盖后来内容；与"只追加"语义一致 | 跨平台语义、单次写入完整性、崩溃半截交易、并发写入交错和恢复复杂度 |

**建议**：先做故障注入测试，再选择平台支持范围内更可靠的方案。不要仅凭"rename 是原子的"就宣称整个提交事务是无竞态的。

不论最终选择哪种原语，事务 journal 至少包含：`commit_id`、`draft_id`、`validation_id`、`before_revision`、`before_hash`、`expected_after_hash`、`write_target`、写入片段 hash、`PREPARED/COMMITTED/RECOVERY_REQUIRED` 状态和快照位置。

## 8. 外部变化的"撤销"策略

| 类型                           | v0.1 处理                                                    |
| ------------------------------ | ------------------------------------------------------------ |
| 内核刚完成的提交               | 提供与 `commit_id` 绑定的撤销入口；检查其后是否存在依赖/外部变化 |
| 用户直接编辑的格式性修改       | 可生成反向 patch 或恢复建议；只有无冲突且用户确认后才应用    |
| 外部新增/修改了已入账交易      | 不直接删除；优先生成新的会计修正/冲销提案并引用原交易        |
| 外部同步引入冲突               | 保存双方可用版本和差异，提示人工解决；不自动选择一方覆盖     |
| 内核关闭期间的修改且没有旧快照 | 只能报告检测到的新 revision；无法保证还原完整 diff 或提供无损撤销 |

这里的"可撤销"应理解为：**内核能够提供受约束的撤销/恢复工作流**，不是承诺任意外部写入都能一键无损还原。

## 9. v0.1 的最小接口

### 9.1 查询

- `get_status()`：账本状态、当前 revision、Beancount 校验状态、是否有外部变更待处理。
- `list_accounts()`：账户树、账户定义摘要和派生状态。
- `get_account(account_name)`：账户详情与契约。
- `get_balance(account_name, as_of)`：派生余额。
- `list_observations()`：外部变化观测事件及来源归因状态。

### 9.2 提案与审核

- `submit_draft(payload, idempotency_key)`
- `get_draft(draft_id)`
- `validate_draft(draft_id)`
- `get_draft_diff(draft_id, validation_id)`
- `approve_draft(draft_id, validation_id, expected_ledger_revision, expected_contract_revision)`
- `reject_draft(draft_id, reason)`
- `withdraw_draft(draft_id)`

Agent 可查询和提交草稿，不得调用批准接口。v0.1 所有批准必须经用户前端/CLI 完成。

### 9.3 外部变化与恢复

- `scan_ledger()`：主动重算 revision 并重新加载。
- `inspect_observation(observation_id)`：查看变化文件、diff 和归因信息。
- `propose_external_revert(observation_id)`：生成恢复建议，不直接执行。
- `recover_commit(commit_id)`：处理内核事务中断；不得对外部编辑做静默恢复。

## 10. 纵向原型实施顺序

### P0-A：Beancount Adapter 与真实账本基线

**目标**：证明内核能在不重写 Beancount 语义的前提下，可靠加载用户真实账本。

- 固定一个 Beancount 版本和 Python 运行环境。
- 使用官方 `loader.load_file()` 完整加载。
- 输出账户树、账户余额、校验错误和 source metadata。
- 验证 include 闭包枚举方法。
- 验证已有插件的行为、临时工作区复现能力和副作用风险。

**验收**：真实账本、包含 include 的样例账本、带 balance assertion 的样例、含已知错误的样例都能得到可解释结果；同一版本环境输出一致。

### P0-B：Revision Observer

**目标**：证明用户/Agent 外部编辑不会被内核覆盖，并能被及时识别。

- 枚举 ledger 文件闭包。
- 每个文件 SHA-256，生成整体 revision。
- 维护上一个已观测 revision。
- 修改 root/include/`write_target` 任意文件后都可检测。
- 校验新的账本 revision；失效旧草稿。
- 保存 external observation；有基线时提供 diff，无基线时诚实报告 diff unavailable。

**验收**：在内核开启期间和关闭期间分别手工修改文件，都能在下次扫描发现；无效 Beancount 文件会阻止内核受控提交；不会自动恢复旧文件。

### P0-C：Draft + Dry-run

**目标**：验证提案协议和完整校验。

- 实现不可变 Draft JSON schema 和 idempotency key。
- 草稿绑定 ledger/contract revision。
- 临时账本副本中仅追加候选交易。
- 运行官方 Beancount 完整校验和账户契约检查。
- 生成 transaction/account/file diff。

**验收**：重复提交不会产生重复草稿；校验基线变化使旧 validation 失效；语法错误、账户未开立和硬契约错误均阻断批准。

### P0-D：Human Approval + Controlled Commit

**目标**：验证唯一自动化写入入口。

- CLI 展示草稿、证据、错误、警告和 Diff。
- 批准绑定 draft/validation/revision 三元组。
- 一个固定 `write_target`，只追加完整交易块。
- journal、写前快照、写入后检查和崩溃恢复。
- 故障注入测试覆盖每个提交阶段。

**验收**：交易只写入一次；重复 approve 不重复提交；批准后文件变化则拒绝提交；模拟进程中断后能恢复或明确进入人工恢复状态。

### P0-E：MCP Adapter

只有 P0-A 至 P0-D 的 Core 用例稳定后才接 MCP。MCP 仅包装相同应用服务，不得在 MCP 层重新实现账户校验或提交逻辑。

## 12. 当前仍然开放的工程决策

以下不应阻止先做 P0-A，但必须在提交实现前解决：

1. **Beancount 版本**：明确 v0.1 固定支持的版本范围，升级通过真实账本回归测试。
2. **include 闭包发现**：选择可靠的文件依赖收集实现；不能假设 API 提供未承诺字段。
3. **外部快照保留策略**：保存所有 ledger 输入文件的内容寻址快照，还是只保存 write_target 与 Git 可追溯的文件。
4. **提交原语**：经过故障注入和并发写入实验后，在临时文件原子替换与 append 写之间作出平台明确的选择。
5. **历史错误基线**：v0.1 是否要求 ledger 初始状态完全通过 Beancount 校验；当前建议要求干净基线。
6. **账户契约存储**：YAML 文件 schema 与版本迁移策略。
7. **MCP 传输**：先 stdio 还是 loopback HTTP；不影响 Core 的先行开发。

## 13. 最优先的下一项工程行动

**先完成 P0-A：在一份可备份的真实 Beancount 账本上，做一个最小 Python Adapter 原型。**

原型只需要：

1. 加载 root file；
2. 调用官方 loader；
3. 记录 entries/errors/options；
4. 可靠列出 include 文件闭包；
5. 输出账户树和余额；
6. 生成基于 SHA-256 的 revision manifest；
7. 在临时目录复制账本、向固定 `write_target` 追加测试交易并再次加载。

P0-A 通过后，P0-B 再处理外部修改观测。不要一开始就做完整 UI、MCP server、移动端或自动审核分级。

**最优先的架构风险不是界面，而是：在用户可任意直接编辑的前提下，内核能否可靠建立账本文件闭包、识别外部 revision 漂移，并在不覆盖用户修改的情况下完成受控追加。**
