# v0.2 账户层设计（草案，待评审）

- **状态**：已评审，待实现（2026-11-16）；实施拆解见 [v0.2 账户层实施计划](v0.2-account-layer-plan.md)。
- **范围**：账户契约编辑、账户状态与对账、账户级审核。
- **依据**：[顶层设计摘要](design-summary.md) 的“账户是产品核心”与账户语义三层；[v0.2 范围](v0.2-scope.md) 修订 1；ADR-018/019/020（本目录 `adr/`）。
- **产品定位**：独立本地账户内核，不计划与 Beancount-Trans 或特定产品集成；解析/导入/报表/同步是外部可选能力。
- **评审（2026-11-16）**：对账不要求证据；对账永不阻断写入；支持可选的申报余额与差异（只读展示）；发布前允许推翻旧设计，约定见 `AGENTS.md`。

## 1. 目标与非目标

**目标**

1. 把账户语义第三层（契约）做深：可安全编辑、可解释、可审计，而不是让用户手改 YAML 后祈祷。
2. 补上账户状态第二层：对账是明确的工作流事实，有记录、有状态、可撤销，不伪装成 Beancount 语义。
3. 审核从“逐笔交易”转向“按账户组织”，但不改变批准绑定与安全不变量。
4. 让个人用户能独立拥有并管理自己的账本；不引入服务端、账号体系或产品绑定。

**非目标（v0.2）**

- 不做完整审核前端（TUI/Web 留到 v0.3）。
- 不做自动审核分级/自动提交；契约成熟后再评估（原设计保留方向）。
- 不做 CSV/账单解析器；外部导入端提供结构化交易。
- 不改变“账本文件是财务事实唯一真相源”“单文件追加”“人工批准”三条不变量。
- 不支持多 `write_target`、删除/改写历史交易。

## 2. 设计原则

1. **财务事实 vs 工作流事实**：账户定义、余额、交易来自 Ledger；契约与对账记录是内核元数据/工作流事实，不能改变 Ledger 的权威地位。
2. **派生优先**：余额、生命周期、最后记账日、待确认草稿数可重建；对账状态由对账记录 + 当前日期推导，不手工维护状态字段。
3. **显式人类动作**：契约应用、对账标记/撤销都必须由人执行并显式确认；Agent/MCP 不获得这些写入口。
4. **fail-closed**：契约无效、CAS 冲突、账本无效、账户不可对账时拒绝操作，不静默修复。
5. **可审计**：契约变更、对账、撤销都进入哈希链审计；`state.json` 只是可重建缓存。

## 3. 账户状态模型

### 3.1 三层与本设计新增

| 层 | 内容 | 来源 | v0.2 变化 |
| --- | --- | --- | --- |
| 定义 | 开立/关闭、层级、别名、货币、booking | Ledger + 契约 | 只读，不新增写路径 |
| 派生状态 | 余额、生命周期、最后记账日、待确认草稿 | Ledger/工作流计算 | 新增 `assertion` 摘要与 `reconciliation` 视图 |
| 契约 | 允许 Agent/币种/标签、对账节奏、余额区间、未管理账户 | `contracts.yaml` | 新增安全编辑入口与覆盖信息 |
| 工作流事实 | 对账记录与撤销 | 审计链（新增事件） | 新增 |

### 3.2 对账记录

一次对账记录（append-only，作为审计事件 `AccountReconciled` 写入）：

```json
{
  "reconciliation_id": "rec_...",
  "account": "Assets:Bank:Checking",
  "as_of": "2026-11-30",
  "ledger_balances": {"CNY": "1234.56"},
  "declared_balances": {"CNY": "1234.00"},
  "differences": {"CNY": "-0.56"},
  "ledger_revision": "sha256:...",
  "contract_revision": "sha256:...",
  "actor": {"type": "human", "id": "local-user"},
  "recorded_at": "2026-11-30T20:10:00Z",
  "note": "与银行 App 月末余额一致"
}
```

- 记录的是“某账户在 `as_of` 日终、在该 revision 下的账本余额快照 + 用户申报的实际余额 + 人的确认”，不是 Ledger 的一条指令。
- `declared_balances` / `differences` 可选：用户不申报时为空；`differences = declared - ledger`（按申报的币种逐项计算）。
- 差异只记录、只展示；**不自动生成调整分录、不自动提交**；需要调整时仍走草稿 → validate → approve → commit。
- 不改变 `ledger_revision`；只追加审计事件并刷新 `state.json.reconciliations` 缓存。
- 撤销：追加 `AccountReconciliationReverted {reconciliation_id, reason, actor}`；只能撤销该账户最新的有效记录，旧记录不可回溯撤销。
- 同一账户同一 `as_of` 不允许两条有效记录；需先撤销再重记。

### 3.3 对账状态推导

契约 `policy.reconciliation.cadence`（`weekly/monthly/quarterly/yearly`）驱动：

| 状态 | 条件 |
| --- | --- |
| `not_configured` | 契约未设 cadence |
| `never` | 有 cadence，但无有效记录 |
| `current` | `today <= last.as_of + cadence_days` |
| `overdue` | `today > last.as_of + cadence_days` |

`accounts show` 返回：

```json
{
  "reconciliation": {
    "status": "current",
    "last": {
      "reconciliation_id": "rec_...",
      "as_of": "2026-11-30",
      "recorded_at": "...",
      "differences": {"CNY": "-0.56"}
    },
    "difference_status": "nonzero",
    "next_due": "2026-12-31"
  }
}
```

- `difference_status`：`none`（未申报）/`zero`/`nonzero`；只用于提示与审核排序。
- 对账状态**永不阻断**写入；`hard_deadline` 字段在 v0.2 视为已弃用：兼容读取但不产生行为，未来 schema 版本移除。
- 对账状态是**日期驱动**的，不因后续提交/外部变化自动失效；历史记录带 revision 仅供审计。
- `state.json.reconciliations` 是缓存：缺失或损坏时从审计链重建；不把缓存当真相。

### 3.4 余额断言摘要

- `last_assertion`：该账户最近一条 Beancount `balance` 指令的日期与金额；没有则为 `null`。
- `assertion_status`：`unset`（无断言）或 `asserted`（有断言且账本加载无错误）。
- 断言失败会让整本账加载报错，归入全局 `LedgerInvalid`，不在账户视图里伪装成“该账户通过”；账户视图只展示断言的存在与日期。

### 3.5 命令与确认

```bash
ledger-kernel accounts reconciliation list Assets:Bank:Checking
ledger-kernel accounts reconcile Assets:Bank:Checking --as-of 2026-11-30 \
  --declared CNY=1234.00 --note "与银行 App 一致" --confirm Assets:Bank:Checking
ledger-kernel accounts reconciliation revert rec_... --reason "余额抄错" --confirm rec_...
```

- `--confirm` 必须等于账户名（撤销时为 reconciliation_id），非交互模式不允许省略。
- 对账前要求：账本加载无错误、账户在 `as_of` 已开立/未关闭、`as_of <= today`。
- 失败返回稳定错误码 `RECONCILIATION_INVALID`；不写入任何记录。
- MCP 不暴露对账写入口；CLI/Python API 只对本地人类操作者开放。

### 3.6 对账不阻断写入（已定）

- v0.2 对账状态只用于提示、排序和审核视图，**不阻断**任何草稿 validate/approve/commit。
- `policy.reconciliation.hard_deadline` 视为已弃用：兼容读取、忽略其值，不产生任何行为；未来 schema 版本移除。
- 任何“逾期阻断”都需要新 ADR，且必须配显式 override；当前不做。
- `CONTRACT_RECONCILIATION` 的判据从“最后记账日”切到“对账状态”，与 ADR-018 对齐。

### 3.7 申报余额与差异（已定）

- `accounts reconcile` 支持可选的 `--declared CUR=VALUE`（可重复，如 `--declared CNY=1234.00 --declared USD=100.00`）。
- 记录 `ledger_balances`、`declared_balances`、`differences`；差异按申报币种逐项计算 `declared - ledger`。
- 申报币种不在账本余额中时，按 `ledger = 0` 计算并在输出中标记，不拒绝记录。
- 差异只读展示，不自动生成调整分录、不自动提交；需要调整时仍走草稿流程。
- 金额必须是十进制字符串；拒绝 float。
- 不改变对账状态、写入路径与其他安全不变量。

## 4. 契约模型与编辑

### 4.1 schema 扩展（向后兼容）

`contracts.yaml` 保持 `schema_version: 1`，新增可选顶层字段：

```yaml
schema_version: 1
unmanaged_accounts:
  - Assets:Savings:Cash
accounts:
  Assets:Bank:Checking:
    aliases: [工资卡]
    policy:
      allowed_agents: [receipt-agent]
      allowed_currencies: [CNY]
      allowed_tags: [recurring]
      required_tags: []
      reconciliation:
        cadence: monthly
        hard_deadline: false
      balance_policy:
        mode: warn_only
        min: null
        max: null
```

- `unmanaged_accounts`：用户显式声明“知道该账户存在，但暂不纳入契约管理”；与 `accounts` 不允许重叠；账户名仍须是合法 Beancount 账户。
- 现有 v0.1 契约文件无需改动即可继续加载；新增字段仅新内核识别，旧内核会因严格未知字段检查拒绝——升级时同版本使用。
- 契约覆盖率 = 有契约的活跃账户 / 活跃账户；`unmanaged_accounts` 单独计数并在 `accounts list --coverage` 中展示。

### 4.2 编辑命令

```bash
ledger-kernel contracts show
ledger-kernel contracts validate --file contracts.new.yaml
ledger-kernel contracts diff --file contracts.new.yaml
ledger-kernel contracts apply --file contracts.new.yaml \
  --expected-current sha256:<current> --confirm sha256:<new> --note "加电费契约"
```

- `show`：当前解析结果、`contract_revision`、错误（若有）。
- `validate`：严格解析；输出错误/警告与覆盖率；不写文件。
- `diff`：与当前文件做统一 diff，输出受影响账户。
- `apply`：唯一写入入口；要求 `--expected-current` 与 `--confirm` 两个哈希，防并发覆盖与误写。
  - 缺少 `--expected-current` 时，非交互模式拒绝（`CONTRACT_CONFLICT`）。
  - 当前文件不存在时 `--expected-current absent`。
- 契约文件写入使用同目录临时文件 + fsync + `os.replace` + 目录 fsync（复用现有原子写工具），持有 `kernel.lock`。
- 写入前把旧/新内容存入内容寻址 blob，审计事件：

```json
{"event_type": "ContractChanged",
 "before_sha256": "sha256:...", "after_sha256": "sha256:...",
 "actor": {"type": "human", "id": "local-user"}, "note": "..."}
```

- `contract_revision` 变化会使所有 pending validation/approval 失效（沿用现有绑定规则），下一次操作时自动重验；不在 apply 内批量重验。

### 4.3 校验规则

- 严格 schema：未知字段、重复别名、非法账户名、cadence 非法、余额区间 min > max 一律拒绝。
- 契约引用未在 Ledger 出现的账户：`validate` 给 warning，允许保存（为未来开户预置）；提交时按现有规则处理。
- `unmanaged_accounts` 与 `accounts` 重叠、重复、非法账户名：拒绝。
- 不允许契约编辑改变 Ledger；如用户需要新账户，先编辑账本 `open`，再改契约。

## 5. 账户级审核

### 5.1 视图

```bash
ledger-kernel review --by-account
ledger-kernel review --account Assets:Bank:Checking
```

输出按账户分组：

```text
== Assets:Bank:Checking  开立  CNY 1234.56  对账 current（下次 2026-12-31）
   contract: 有  允许 agent: receipt-agent  币种: CNY
   待审: drf_...  2026-11-30  99.90  Expenses:Home:Utilities
         drf_...  2026-11-30  46.90  Expenses:Home:Utilities
```

- 每组展示：生命周期、余额、对账状态、契约摘要、待审草稿、契约警告。
- `--account` 只过滤该账户；不改变批量批准入口。

### 5.2 批准语义不变

- 不引入“账户级批准对象”。批准仍绑定 `draft_id + validation_id + ledger_revision + contract_revision`。
- 账户分组只是视图；批量批准仍要求显式 draft_id 列表与 `--confirm`。
- 这样不改变状态机、审计事件和 ADR-013 的沿用规则；账户级快捷操作留到 v0.3 评估。

## 6. CLI / API 汇总

| 入口 | 读/写 | 说明 |
| --- | --- | --- |
| `contracts show/validate/diff` | 读 | 严格解析与差异 |
| `contracts apply` | 写 | 原子替换契约 + 审计；人类确认 |
| `accounts show` | 读 | 新增 reconciliation/assertion 摘要 |
| `accounts list --coverage` | 读 | 契约覆盖率、unmanaged 列表 |
| `accounts reconcile` | 写 | 追加对账记录；人类确认 |
| `accounts reconciliation list/revert` | 读/写 | 历史与撤销 |
| `review --by-account/--account` | 读 | 账户分组视图 |
| Python API | 写 | 与 CLI 同一用例；不新增绕过路径 |
| MCP | 读/提案 | 不暴露契约/对账写入口 |

## 7. 存储与迁移

| 数据 | 位置 | 可重建 |
| --- | --- | --- |
| 契约 | `.ledger-kernel/contracts.yaml` | 否（版本化文件） |
| 对账记录 | `.ledger-kernel/audit/events.jsonl` | 否（审计链） |
| 对账缓存 | `.ledger-kernel/state.json.reconciliations` | 是（从审计重建） |
| 契约变更前/后内容 | `snapshots/blobs/<sha>` | 是（blob 去重） |

迁移：

- 既有 `contracts.yaml` 不需要改；新字段可选。
- 旧版本内核遇到新字段会 `CONTRACT_INVALID`，因此升级后所有内核实例必须同版本使用。
- `state.json` 缺 `reconciliations` 时按审计链重建；不需要手工迁移。
- 不新增 Ledger 文件，不改变 `ledger_revision` 的构成。

## 8. 安全不变量

1. 契约/对账操作不写 Ledger；Ledger 仍只由 `commit` 写入。
2. 所有元数据写入持 `kernel.lock`，失败关闭；不自动修复。
3. 契约应用与对账/撤销都必须显式确认；非交互拒绝模糊确认。
4. 契约变更使 pending validation/approval 失效；不沿用未经新契约验证的批准。
5. 对账记录append-only；撤销也是新事件，不删除历史。
6. 不新增自动批准路径；审核分级仍不在 v0.2。
7. 不引入服务端/账号体系；actor 仍是本地 `human/local-user`，不伪造身份。

## 9. 验收测试

- 契约 apply：合法文件成功、原子写入、审计 `ContractChanged`、blob 前后内容可读。
- 契约 apply：CAS 不符 → `CONTRACT_CONFLICT`，文件不变。
- 契约 validate：未知字段/重复别名/重叠 unmanaged → `CONTRACT_INVALID`，不写。
- 契约变更使 pending validation 失效，重验后才可批准。
- 对账：记录成功、`accounts show` 状态 `current`；过期后 `overdue`；无 cadence `not_configured`。
- 对账：账本无效/账户未开立/as_of 未来/重复 as_of → `RECONCILIATION_INVALID`，不写。
- 撤销：只能撤销最新有效记录；撤销后状态回退；历史保留。
- 账户级 review：分组正确、契约/对账摘要正确、批量批准仍按 draft_id 绑定。
- 迁移：无新字段的旧契约可加载；缺缓存时从审计重建。
- 不变量：契约/对账操作前后 `ledger_revision` 不变。

## 10. 待决问题

1. **大量审计事件下的缓存重建/性能上限**：v0.2 先按需扫描 + `state.json` 缓存；超过阈值再引入索引。
2. **未来是否移除 `hard_deadline` 字段**：当前兼容读取并忽略；下一次 breaking schema 版本移除。

已定：契约 schema 保持 `version: 1` 加法扩展（发布前可直接升 2）；对账不要求证据；对账永不阻断；申报余额差异只读。
