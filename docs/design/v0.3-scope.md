# v0.3 范围与明确非目标（MVP：审核闭环）

- **状态**：已冻结（2026-11-16，文档先行；代码未开始）。
- **修订**：2026-11-16 修订 1 —— 新增第 4 节「前端形态与宿主」与 D13；明确“同仓库独立安装单元、不绑定 Agent 宿主”的边界。
- **依据**：
  - v0.2.0 已发布：账户契约编辑、账户对账、账户级审核；
  - v0.2.x 账户层 dogfood 基线轮（[v0.2 账户层 dogfood 轮次报告](v0.2-dogfood-round2.md)）；
  - dogfood 1 写入闭环指标（[v0.2 范围建议](v0.2-scope.md)）；
  - 顶层设计摘要：账户是产品核心、Agent 外置、前端可替换，内核只做账户语义、受控写入与审计/恢复。
- **一句话**：v0.3 只做“审核闭环”，且前端外置；本文最重要的交付是**明确不做什么**，防止 MVP 膨胀为功能大礼包。

## 1. MVP 定义

在不扩大内核职责的前提下，把已被数据证明的“审核往返”做顺：

1. 真实账户层 dogfood（2–4 周，按 [dogfood 协议](../dogfood.md)）；
2. 一个内核之外的极简审核前端（TUI 优先）；
3. 只做 dogfood 暴露且被计量的内核修复。

内核不新增领域语义、不新增写入路径、不新增服务端。

## 2. 为什么是审核闭环

- 唯一被数据命中的瓶颈：提交→批准中位 **69.5 秒 > 60 秒**（dogfood 1）。
- v0.2 已解决“按账户组织”和读取性能（`review --by-account` 在真实账本副本上约 0.88 秒/次），缺的是交互层。
- 归因没有证据：dogfood 观测事件 **0**；协议判据 #4 要求至少 3 次无法解释的观测才考虑归因。
- 单 `write_target` 是样本的真实用法，也是单文件追加、原子替换、journal 与恢复的基础；没有跨文件需求证据。
- 目标用户是本地个人；服务端、账号体系、同步不是内核职责。

## 3. 明确不做（本文核心）

> 非目标不是永久否决。每项都写明“重新讨论条件”；未满足条件前不排期、不写代码，代码评审以本表为准。

| 编号 | 明确不做 | 原因 / 证据 | 重新讨论条件（re-open gate） |
| --- | --- | --- | --- |
| D01 | 把 TUI/Web、服务端、账号体系、同步放进内核 | 内核只做账户语义、受控写入与审计/恢复；交互属于外部适配器 | 外部适配器确实无法满足，且有真实用户数据；先修订本文并补 ADR |
| D02 | Web 审核（MVP 先 TUI） | TUI 无服务端、无鉴权、攻击面最小，符合本地个人定位 | TUI 实测不达标（需要图片凭证、远程、多设备等）且有数据；先修订本文 |
| D03 | 多 `write_target`、多文件事务、删除或改写历史 | 与单文件追加、原子替换、journal 恢复与审计不变量冲突，复杂度不成比例 | 真实用户跨文件需求 + ADR + 恢复与原子性设计；否则不做 |
| D04 | 按需归因（Git/OS audit） | 不改变财务事实与可执行动作；dogfood 观测为 0，没有需求证据 | 真实 dogfood 中至少 3 次无法解释的观测（协议判据 #4）；即使做也只能是外部只读工具，不能作为授权依据 |
| D05 | Windows 支持（MVP 明确 POSIX-only） | 移植性成本、非差异化；当前锁与目录 fsync 面向 POSIX | 有真实非 POSIX 用户与使用数据；先做锁/fsync 抽象与 Windows CI，再排期 |
| D06 | 自动审批、自动提交、账户级批量批准 | 人工批准绑定四元组是安全不变量；契约成熟度与审计阈值未到 | 契约成熟 + 可审计阈值 + 撤销窗口 + 新 ADR（顶层设计长期方向，不是 v0.3） |
| D07 | 外部交易冲销助手（MVP） | 定位“哪笔外部交易”属于匹配判断，应留在外部 Agent/前端；内核只接受显式冲销草稿 | 真实错账/退款摩擦数据 + 外部匹配方案；内核仍只走 draft → validate → approve → commit |
| D08 | 导入、CSV、报表、预算、分析仪表盘 | 外部生态能力，不是内核职责 | 不设 gate；如做也是独立产品/适配器 |
| D09 | 契约自动修复、硬余额策略、自动对账、对账证据要求 | 契约与对账是声明式配置/工作流事实；自动修复会掩盖错误 | 新 ADR + 真实数据；对账“永不阻断”语义不得改 |
| D10 | 身份认证、多用户、权限系统 | 内核是本地单用户；actor 固定 `human/local-user`，不伪造身份 | 产品定位变化时另立项目；不在内核内加 |
| D11 | 破坏性 schema/CLI 变更（`hard_deadline` 移除、改名） | v0.3 以审核闭环为主，兼容性优先 | 下一次 breaking 版本（设计 3.6/10 已记录）；单独发布说明 |
| D12 | 未被数据证明的重构/微优化 | 先量化再优化，避免为“看起来更优雅”改内核 | 有真实 dogfood 数据或明确缺陷；保持不变量 |
| D13 | DSH 等特定 Agent 宿主插件作为 MVP 审核前端 | 宿主内 Web UI，绑定特定客户端；批准面不应与 Agent 同宿主；违背 D01/D02 与“前端可替换” | 外部 TUI/CLI 稳定 + 真实用户主要使用该宿主 + 仅只读便利层定位；先修订本文并补 ADR |

补充边界：

- 不引入 AI 推理、模型调用、自动分类。
- 不新增网络监听端口；MCP 仍为 stdio。
- 不把真实账本、`.ledger-kernel/`、证据文件提交进仓库。
- 不为 UI 方便而放宽 `--confirm` 或四元组绑定。

## 4. 前端形态与宿主

**结论**：审核前端是**同仓库、内核之外的独立安装单元**；MVP 不另起仓库，也不做 DSH 等特定 Agent 宿主插件。内核保持零前端依赖。

### 4.1 三种“另起”的边界

| 形态 | 现在是否做 | 说明 |
| --- | --- | --- |
| 独立安装包/目录 | ✅ 做 | 同仓库 `frontends/review-tui/`，自带 pyproject、测试与入口；`ledger_kernel` 不 import 它、不默认安装它 |
| 独立仓库 | ⏳ 暂不 | 提取条件见 4.3；MVP 需频繁联调 JSON 契约与 dogfood 指标，同仓共享 fixture、e2e 与 CI |
| 独立产品 | ❌ 不做 | 内核是产品核心；审核前端只是可替换的壳 |

### 4.2 交互契约（前端不碰内核内部）

- 只读：调用 `review --json`、`accounts list`、`accounts show`、`contracts show`；不 import `src/ledger_kernel` 内部模块。字段与稳定性规则见 [v0.3 前端只读 JSON 契约](v0.3-frontend-contract.md)。
- 写入：只调用现有 CLI（`drafts validate` / `drafts approve --confirm`）或公共 Python API；不新增写入路径，不复制业务校验逻辑。
- 批准必须人工输入确认；前端不得提供跳过确认、自动批准或账户级一键批准。
- 无网络监听、无服务端、无账号；首版为标准库 TUI，200–400 行量级。
- 契约防漂移：内核仓库保留只读 JSON 的 golden 测试；前端 CI 固定 `ledger-kernel` 版本区间。

### 4.3 拆仓（提取）条件

满足任一条件即评估拆为独立仓库：

- 前端超过约 1–2k 行，或引入非标准库 UI/服务端依赖；
- 需要独立发布节奏或独立版本号；
- 出现第二个前端（Web/桌面/移动），需要并列维护；
- 同仓 CI 时间或评审边界明显被前端拖累。

拆仓只分离安装单元与发布节奏，不改变内核 API。

### 4.4 为什么 MVP 不做 DSH 等 Agent 宿主插件

- 属于宿主内 Web UI，违反 D02（MVP 先 TUI、不做 Web）与 D01（交互不进内核），并新增 D13。
- 审核面只在某个 Agent 客户端可用，其他客户端（终端、Claude Desktop 等）没有，违背“前端可替换、不绑定特定产品”。
- DSH 同时运行 Agent；把批准按钮放进同一宿主会模糊“Agent 不能批准”的边界，prompt 注入或自动化误触风险更大（MCP 刻意不暴露 approve）。
- 插件需要 host bridge 访问本地文件/CLI，并跟随宿主版本与 HMR 变化；MVP 用不到这些复杂度。
- **后续位置**：DSH 插件只能作为可选只读便利层（显示待审数量、打开外部 TUI、辅助生成草稿）；审批权威仍在外部 TUI/CLI，内核不感知宿主。

## 5. MVP 要做什么（同样要窄）

1. **外置审核前端（TUI 优先）**：同仓库 `frontends/review-tui/`（独立可选包，200–400 行量级，优先标准库）；只读列表 + 草稿详情/diff/checks + 显式确认后逐 draft 批准；只通过 CLI JSON / CLI 写入与内核交互，不进入 `src/ledger_kernel/`，不新增内核依赖。
2. **只读 JSON 面固化**：`review --json`、`accounts list`、`accounts show`、`contracts show` 的字段作为适配器契约（见 [v0.3 前端只读 JSON 契约](v0.3-frontend-contract.md)）；不新增领域语义。
3. **真实 dogfood**：按协议 2–4 周、至少 20 笔，覆盖收入、账户间转账、冲销、非零差异与 cadence 稳态；采集判据 #2 与账户层 #6–#9。
4. **有计量的内核修复**：只修 dogfood 暴露的缺陷/性能；不改批准、审计、写入、对账语义。

## 6. 验收与决策门

**MVP 验收**

- 真实 dogfood 的提交→批准中位耗时 < 60 秒；
- 内核包、依赖与 CLI 命令面不增加（前端在外部）；
- 审计链、批准绑定、`ledger_revision` 等不变量零回退；
- 真实轮次数据与结论写入 `docs/design/`。

**顺序**

1. 先跑真实 dogfood（不改功能），确认耗时与摩擦；
2. 外置 TUI 按数据迭代；
3. 达标后冻结“v0.3 = 审核闭环”；其他候选只进入 v0.4+ 讨论。

若 TUI 不达标，再评估 Web（仍需修订本文）；不跳到自动审批。

## 7. 与现有设计/约束的关系

- 不改变 ADR-012～ADR-017 的写入、批准、审计不变量。
- 不改变 ADR-018/019/020 的账户层语义；`review --by-account` 仍是只读视图。
- 多 `write_target` 仍受 `AGENTS.md` 硬约束；重启必须先写 ADR。
- 本文先于实现冻结；实现越界视为范围变更，先修订本文或新增 ADR。

## 8. 变更控制

- 修改本表任一条“不做”需要：真实数据 + 本文修订（必要时 ADR）。
- 新增候选默认进入 v0.4+ 讨论，不插入当前 MVP。
- 代码评审检查：这个改动是否让 `ledger_kernel` 包新增 UI、网络或匹配职责？是则拒绝或移到适配器。
