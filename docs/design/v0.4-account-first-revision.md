# v0.4 账户优先：分域真相与账户注册表（草案）

- **状态**：草案修订 2（2026-11-17，未冻结）。只对齐设计，不动代码；冻结前不改 v0.3 已冻结范围。
- **修订 2 推翻的内容**：修订 1 的“账本唯一真相”“账户定义只读”“审核为 MVP 中心”“账户名承载完整语义”“存量账户原样收编”五项假设。理由见第 11 节。
- **触发**：维护者 2026-11-16/17 的方向判断——战略目标是用户拥有账本，账户是地基；账本不再是唯一真相源，账户定义以注册表为准；MVP 可不做审核工作流；用户侧只有别名；地址采用“语义路径 + 不透明叶子”的混合方案。
- **依据**：[顶层设计摘要](design-summary.md)、[v0.2 账户层设计](v0.2-account-layer.md)、[v0.3 前端契约](v0.3-frontend-contract.md)、ADR-012/015/018/019/020、`AGENTS.md` 的预发布条款、Beancount 3.2 实测约束。
- **不在本文范围**：审核自动化（分级、自动放行、Agent 代批准）；账单解析/导入；报表实现。

## 0. 一句话

**用户拥有模型，账本记录事实。** 注册表是模型域的真相源，账本是事实域的真相源；审核不再是 MVP 的中心，而是非用户写入进场时的闸门。

```text
意图（注册表）  ──plan/apply──▶  事实（账本）  ◀──observe──  手改 / 外部导入
      ▲                              │
      └──────── audit ◀──────────────┘
```

## 1. 目标与判据

“用户拥有账本”拆成四层，现状与目标：

| 层 | 含义 | 现状 | v0.4 目标 |
| --- | --- | --- | --- |
| 文件拥有 | 纯文本、本地、可导出 | 已具备 | 保持 |
| **语义拥有** | 账户/命名/结构由用户定义，可改 | **弱** | 注册表权威 + 命名层 |
| 过程拥有 | 录入、对账、修正由用户拍板 | 强 | 保留确认与校验 |
| 退出拥有 | 可带走全部历史与审计 | 已具备 | 注册表随账本一起导出 |

“账户是地基”操作化为五层契约：

| 契约层 | 内容 | v0.4 动作 |
| --- | --- | --- |
| 分类 | 树形、报表归属 | 组路径 + 别名 |
| 行为 | Agent/币种/标签/余额策略 | 沿用契约，并入注册表 |
| 时间 | 开户/关户、对账周期 | 注册表声明 + 物化 |
| 证据 | 断言、对账记录 | 保持 |
| 变更 | 开户/关户/移动/别名的历史 | 新增审计事件 + successor |

**成功判据**：用户不碰 `.bean`，也能建账户、改别名、调整层级、关账户，并看到账本按预期变化；所有变更可审计、可撤销；账本仍可单独打开、可带走。

## 2. 分域真相

| 域 | 真相源 | 权威属于 | 变更方式 | 载体 |
| --- | --- | --- | --- | --- |
| 模型 | 账户注册表 | 用户 | 显式编辑 + 校验 + CAS + 审计 | `.ledger-kernel/accounts.yaml`（schema v2） |
| 事实 | 账本 | 证据 + 校验 | 只追加，不改写 | `*.bean` |
| 证据 | 原始凭证 | 外部现实 | 只追加引用 | `documents/` 等 |
| 决策 | 审计链 | 用户 | 只追加 | `audit/events.jsonl` |

- “用户是真相源”准确的表述是：**用户是模型域的作者与最终权威**；事实仍由证据与 Beancount 校验约束。用户手改账本是 actual 的漂移，不是模型的变更。
- 账本仍然 append-only。注册表可变，但每次变更走 CAS + 审计，历史不删除。
- `registry_revision` 与 `ledger_revision` 独立；草稿与校验同时绑定两者。

## 3. 命名层：身份、名字、地址

| 层 | 名称 | 谁维护 | 可变性 | 例子 |
| --- | --- | --- | --- | --- |
| 身份 | `id` | 系统 | 永不变、不复用 | `acc_01J...` |
| 名字 | `alias` | 用户 | 可改，账户全局唯一 | `中行工资卡` |
| 地址 | `account` | 系统生成 | 开户后冻结；变更走 successor | `Assets:Savings:Bank:BOC:Acct-7f3a2c1d` |

两层不够：alias 可改不能当主键，account 是科目不能给用户看；必须有第三层稳定 id 解耦。

### 3.1 地址 = 语义路径 + 混合叶子

```text
Assets : Savings : Bank : BOC : Acct-7f3a2c1d
  │         │        │      │        │
  │         └────────┴──────┘        └── 叶子：身份（不透明，隐私）
  │              位置：语义、可报表
  └── 类型：Beancount 强制
```

- **路径是位置**：让 Fava / BQL 能按 `Assets:Savings:Bank:BOC` 前缀汇总，账本保持可读。
- **叶子是身份**：不暴露卡号后四位；不随别名变化。
- **别名是名字**：中文、可改、唯一。

叶子分两种模式：

| 模式 | 叶子 | 适用 | 默认 |
| --- | --- | --- | --- |
| `opaque` | `Acct-<8~12 位十六进制>` | 银行卡、信用卡、同类多实例、隐私敏感 | Assets / Liabilities |
| `semantic` | 语义段，如 `Dining` | 单例科目、支出/收入分类 | Income / Expenses / Equity |

创建时可覆盖默认；同一父级下叶子唯一。不要全量使用 `opaque`——上百个 `Acct-xxx` 会毁掉账本可读性。

### 3.2 Beancount 实测约束

- 中文账户名不合法：`Assets:银行卡` → `Invalid account name`。
- 每段必须 `[A-Z][A-Za-z0-9-]*`：小写开头、下划线不合法；连字符合法。
- 因此裸 UUID 不能当叶子（可能数字/小写开头）；必须加前缀，如 `Acct-7f3a2c1d`。
- `open` 指令可携带 metadata，实测保留：

```beancount
2026-01-01 open Assets:Savings:Bank:BOC:Acct-7f3a2c1d CNY
  alias: "中行工资卡"
```

### 3.3 冻结与变更规则

| 操作 | 是否改账本 | 机制 |
| --- | --- | --- |
| 改账户别名 | 否 | 注册表 + 审计 |
| 改组别名 | 否 | 注册表 + 审计 |
| 改组 segment | 否，但**禁止** | 已有子节点时拒绝；否则会批量换地址 |
| 账户换路径 / 换类型 | 是 | successor：旧归档 + 新账户声明 |
| 合并 / 拆分 | 是 | successor 链 |
| 关账户 | 是 | 追加 `close`；后续记账被 Beancount 阻断 |

- 组 segment 一旦被使用就冻结；要重组只能新建组 + 账户逐个 successor，成本高，MVP 不做批量重组。
- `open` 上的 `alias` 是**开户快照**，不是实时镜像；改名后账本仍旧名，注册表为准。`doctor` 可报告不一致，但不自动改。

## 4. 注册表 schema v2

`contracts.yaml` 升级为 `accounts.yaml`，把组、账户、策略放在同一棵树里；v1 不做兼容。

```yaml
schema_version: 2
groups:
  - {id: grp_assets,  alias: 资产,     segment: Assets,  parent: null,       type: Assets}
  - {id: grp_savings, alias: 储蓄,     segment: Savings, parent: grp_assets}
  - {id: grp_bank,    alias: 银行,     segment: Bank,    parent: grp_savings}
  - {id: grp_boc,     alias: 中国银行, segment: BOC,     parent: grp_bank}
accounts:
  - id: acc_01J...
    alias: 中行工资卡
    segment: Acct-7f3a2c1d
    mode: opaque
    parent: grp_boc
    status: active            # active | archived
    successor_of: null        # 指向旧账户 id
    policy:
      allowed_agents: [receipt-agent]
      allowed_currencies: [CNY]
      reconciliation: {cadence: monthly}
      balance_policy: {mode: warn_only}
```

校验规则：

1. 组与账户的 `id` 唯一；`parent` 必须存在且不成环；根组只能是五类之一。
2. 组路径深度 ≤ 3（类型根之外）；segment 满足 `[A-Z][A-Za-z0-9-]*`；同父下唯一。
3. `mode=opaque` 的 segment 必须是 `Acct-<hex>`；`mode=semantic` 不得与同父下的组名冲突。
4. 账户别名全局唯一（规范化后）；组别名在父级内唯一；归档节点的别名保留，不复用。
5. 已有子节点时禁止修改祖先组的 `segment`；账户 `segment` 开户后冻结。
6. `successor_of` 不得成环；旧账户必须 `archived`，新账户必须 `active`。
7. 未登记但账本中存在的账户列入 `unmanaged_accounts`，只读展示，不自动删除。

写入与审计复用 ADR-019 的模式：严格校验 → `--expected-current` + `--confirm` 双哈希 CAS → 同目录临时文件 + `fsync` + `os.replace` → `RegistryChanged` 审计（前后 hash、actor、note）。

## 5. 写入路径

### 5.1 账户定义

```bash
ledger-kernel accounts create --alias 中行工资卡 --type Assets --path 储蓄/银行/中国银行
ledger-kernel accounts plan                 # registry vs ledger：缺 open、多 open、别名漂移
ledger-kernel accounts apply --expected-current sha256:... --confirm sha256:...
```

- `plan` 只读；`apply` 只追加 `open/close`，不改历史。
- 账户定义写入仍只经 `Kernel`；MCP 不暴露。
- `unmanaged_accounts` 不自动收编。

### 5.2 录入

```bash
ledger-kernel entry add --payload txn.json   # 提交 + 校验 + diff，返回 draft_id
ledger-kernel entry commit drf_... --confirm drf_...
```

- 用户看到的是“预览 → 确认 → 落账”，没有审核队列、没有批量批准。
- 内部仍走 draft/validation/approval：`entry commit` 在人工 `--confirm` 后调用与现有 `drafts approve` 相同的批准函数，再 commit；绑定 `draft_id + validation_id + ledger_revision + registry_revision`。
- 这触碰“不得增加自动批准”的边界，冻结前必须明确：批准动作由人的显式确认触发，审计记录 `actor=human`；如果评审认为“命令内联审批”仍属自动批准，则保留独立 `drafts approve`，`entry` 只做预览与提交。

### 5.3 状态机：折叠，不删除

保留内部状态机（`Submitted / Approved / Committing / RecoveryRequired …`），因为其中四条与审核无关，是写入安全本身：

1. 内容绑定（fragment 哈希 + review digest）；
2. 时效绑定（ledger/registry revision）；
3. 崩溃恢复（journal）；
4. 审计。

只从用户路径上摘掉：审核队列、批量批准、carry-forward、独立的 `drafts approve`。Agent 进场时原样恢复完整状态机。

## 6. 审核：延后，不是删除

- MVP 不做审核工作流，前提是**没有非用户写入、没有批量导入**。
- 保留校验与确认：Beancount 完整加载、增量断言、diff、显式 `--confirm`。
- 审核回归条件（满足任一）：Agent 可提交草稿；批量导入；破坏性操作（关户、迁移）需要二次确认。
- 回归时仍绑定四元组，仍不提供自动批准；MCP 在此之前只读。

## 7. 存量账户与预发布

`AGENTS.md` 的预发布条款允许推翻设计与破坏性 schema/CLI 变更，但**不允许删除或改写审计链、journal、已提交的账本内容**。两者要分开：

| 对象 | 能否推翻 |
| --- | --- |
| schema v1、CLI、注册表格式 | 可以，直接升级，不写兼容层 |
| 已提交的账本交易、审计、journal | 不可以 |
| 测试用账本（TestAssets） | 可由维护者另建新账本；`TestAssets` 原目录仍只读，不由内核改写 |

因此：

- 代码只支持 v2，不写 v1 读取分支；旧格式由一次性迁移脚本处理。
- 存量账户不强制收编。两个可接受路径：
  1. **一次性 adopt**：读账本账户名，建组、建账户（`mode=semantic`，叶子沿用旧段），补别名；不写账本。
  2. **新账本**：直接用新方案开始，旧账本归档。
- 不做“旧命名永久兼容模式”；这是预发布红利，过期不补。

## 8. 分期

| 阶段 | 范围 | 写入 | 审核 |
| --- | --- | --- | --- |
| M1 账户模型 | schema v2、命名层、`plan/apply`、账户工作台只读、`doctor` | 只写 open/close | 无 |
| M2 录入 | `entry add/commit`、diff、确认 | 追加交易 | 无（保留确认） |
| M3 Agent | 恢复 draft/approval，仅对非用户写入 | 提案 | 完整审核 |

M1 验收：

1. 用户不碰 `.bean` 能建组、建账户、改别名、关账户；
2. `plan` 能报出缺 open、多 open、别名漂移、未登记账户；
3. `apply` 失败时账本与注册表都不变；
4. Fava 能按路径前缀汇总，叶子不破坏报表；
5. 所有注册表变更进审计，可重建 `state.json` 缓存。

## 9. 不变量核对

| 约束 | 是否触碰 | 处理 |
| --- | --- | --- |
| 账本 append-only、用户最高编辑权 | 否 | 不变 |
| 唯一受控写入口 `Kernel` | 是（新增注册表写路径） | 仍只经 `Kernel`；CAS + 审计 |
| 人工批准四元组 | 是（对象扩展 + 内联确认待定） | 绑定不变；`contract_revision` 改为 `registry_revision`；内联确认是否算自动批准需 ADR 明确 |
| 审计/journal 不可删改 | 是（新增事件） | 只追加；撤销走反向草稿 |
| 单文件、单 `write_target` | 否 | 注册表是元数据，不是账本目标 |
| ADR-012 增量断言 | 是（账户指令） | 扩展 expected 集合，不放宽逐项相等 |
| ADR-015 digest | 是 | 纳入账户指令 |
| MCP 不暴露写入口 | 保持 | MVP 只读 |
| 审核 | 延后 | 机制保留，用户路径折叠 |

## 10. 未决问题

- **Q1**：状态机选 A（折叠）还是 B（删除）？本文按 A 写；B 需要重写写入令牌，成本不低于保留。
- **Q2**：组别名作用域——父级内唯一（本文）还是全局唯一？
- **Q3**：`opaque` / `semantic` 的类型默认是否够用，是否需要创建时强制选择？
- **Q4**：successor 链的报表连续性由 LK 工作台合并，还是要求 Fava 侧接受分裂？
- **Q5**：存量账本走一次性 adopt 还是新账本？预发布允许后者，但需维护者确认。

## 11. 修订记录：推翻了什么、为什么

| 修订 1 的假设 | 修订 2 的选择 | 理由 |
| --- | --- | --- |
| 账本是唯一真相源 | 分域真相：注册表=模型，账本=事实 | 用户是语义权威；Beancount 表达不了别名/策略/生命周期 |
| 账户定义只读 | 注册表权威，`open/close` 由内核物化 | “账户管理”必须能定义账户，否则名不副实 |
| 审核是 MVP 中心 | 审核延后，保留确认与校验 | 无非用户写入时审核是仪式；录入仍需 preview+confirm |
| 账户名承载完整语义 | 路径=位置、叶子=身份、别名=名字 | 中文不能进账户名；隐私；多实例 |
| 存量账户原样收编 | 不做兼容层，adopt 或新账本 | 预发布允许破坏性变更；兼容层会长期拖累 schema |

被推翻的设计仍留在 `docs/design/` 历史与 ADR 中，不删除；实现以冻结后的 v0.4 范围文档为准。
