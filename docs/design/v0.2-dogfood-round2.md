## 摩擦点（基线证据）

1. **【高】每个公开读/写都全量重载账本**：`_ensure_fresh_locked` 在 `list_accounts` / `get_account` / `reconcile_account` / `get_status` 等每个方法开头重跑 `adapter.load`（Beancount 解析 + 134 文件 sha256）。97 次 `get_account`（90.4 s）与 57 次对账（52.3 s）占整轮 186 s 的 76%。
2. **【高】`review --by-account` 逐草稿、逐账户重复加载**：队列每个草稿调 `get_draft`，分组时每组再 `get_account`；2 组 + 3 草稿 ≈ 5 次全量加载，净耗时 4.75 s，跨 30 个账户的批量审核会线性放大。
3. **【中】对账/审计链 O(n²) 苗头**：每次 `reconcile_account` 会多次扫描全审计链，`audit_append` 每次读全量 events，`state.json` 每笔全量重写；66 事件时是常数项，1k–10k 事件后会变成每操作几十 ms × 3 遍的平方项。
4. **【中】`validate` 单次 2.18 s 是账户层最贵操作**：dry-run 复制 134 文件闭包 + baseline/candidate 两次全量 load + 对 11,920 entries 两次 canonicalize；批量 10 篇约 22 s。
5. **【中/高】账户层状态没有聚合输出**：`list_accounts` 不含 reconciliation/assertion 状态，统计对账及时率/stale 只能逐账户 `get_account`（97 次，占整轮 49%）。
6. **【低】契约编辑往返**：apply 本身不慢，但需要先 view 拿 expected revision、再为 coverage 多做一次 view；`preview_contracts` 已能一次给出 revision + coverage，属使用方式问题。

## 本轮修复（v0.2.x，Unreleased）

| 修复 | 实现 |
| --- | --- |
| 闭包未变时复用已加载的 Beancount 结果 | `Kernel._cached_load_if_unchanged` + `BeancountAdapter.rehash_manifest`：每次操作仍重算整个闭包哈希（外部变化检测语义不变）；只有哈希、契约 revision、engine fingerprint 都一致时才跳过重复解析。前次 load 有错误、closure 回退来源、文件消失等情况强制全量 load。 |
| 批量账户层视图 + review 单次读取 | `list_accounts` 每行新增 `assertion_status` / `last_assertion` / `reconciliation`（与 `accounts show` 一致）；`review --by-account` 用一次 `list_accounts` 取代逐组 `get_account`。 |
| 对账记录进程内缓存 | 按审计文件签名缓存重建结果；任意 audit append 或外部变化后自动重建；读取仍以审计链为真相，`state.json` 仍只是跨进程缓存。 |

未在本轮修复（留待下一轮）：`validate` 的 dry-run 成本、审计 append 的 O(n)、CLI 每进程一次全量 load（这是单次命令的固定成本，本轮未变）。

## 对 v0.3 候选的结论（只基于本轮证据）

- **最高优先：真实 2–4 周账户层 dogfood**。本轮只证明工具链可用与性能改善，不证明采用率：副本操作没有新增真实交易、没有 approve/commit 计时、declared 全为零差异、状态是“刚全部对账完”的 current，未覆盖 overdue/never 稳态、收入/转账/冲销与非零差异。
- **中优先：validate/dry-run 性能**（真实账本 p50 ≈ 1.14 s/笔，10 篇约 11 s）：对应 v0.2-scope 的 P2 批量提交性能；先做 baseline/candidate 复用与 canonical Counter 复用，需补回归测试。
- **中优先：审计链增量写/索引**（1k+ 事件前）：当前 append 每次读全量、state 全量重写；量大后按设计 §10 引入索引，不改审计语义。
- **低/待数据：账户级批量批准**：需真实审核耗时数据与新 ADR，本轮不加入；账户层聚合视图已由 `accounts list` 字段满足，先观察真实轮次是否够用。
- **决策门**：先用真实轮次数据复测 dogfood 判据 #2 与账户层判据 #6/#7/#8，再冻结 v0.3 范围。

## 局限

- 本轮是**副本上的元数据基线轮**，不是协议要求的 2–4 周增量使用；不产出“采用率/审核耗时”结论。
- declared 一律等于账本余额，未覆盖非零差异、申报错误与多币种差异解释。
- cadence 统一 monthly；状态分布是全部对账后的 current，不是稳态 overdue/never。
- 单机单 OS（POSIX、本机 Python 3.14）；Windows 与大账本（>1k 审计事件）未测。
- 性能绝对值受硬件影响，看相对比例；脚本会打印环境版本。
